## 2026-11-06

- Public demo mode for the portfolio: a "try it" button on the login page creates a trial technician account with no sign-up and logs the visitor in. User-chosen over a sign-up form (friction, personal data/GDPR) and over shared per-role demo accounts. Off by default (`APP_DEMO_ENABLED`), on in the `dev` profile; never meant for a real deployment.
- Cleanup: user chose to purge expired trial accounts (24 h, `APP_DEMO_TTL_HOURS`) with everything they created, rather than a nightly full reset of the database. The purge also makes the trial accounts' JWTs useless even though tokens never expire, since `JwtFilter` reloads the user on every request. Verified against the local dev DB: the ticket, history, assignment, classification, article and activity rows go away and the seed data stays untouched.
- Purge only is safe if visitors can't alter shared seed data. User's rule: prefer existing technician ownership rules, and only restrict trial accounts where those rules can't cover it. Trial accounts are rank 0 technicians (real ones start at rank 1), not a new role. They can't comment (a comment can go on any ticket; user wants comments open for real technicians) and can only edit the knowledge articles they wrote. Deleting articles was already admin-only, and workflow actions (closing included) were already limited to the assigned technician.
- Clarified closing rule (user): a technician closes a ticket they created only by self-assigning it and following the workflow, never one a manager assigned to another technician. A "creator can close" change made on a misreading was reverted; a unit test now locks the rule.
- Abuse limits: 3 trial accounts per IP per hour, 200 active at most. Trial accounts are left out of the manager workload list. Deploy caveat: behind a reverse proxy, `getRemoteAddr()` is the proxy's IP, so `server.forward-headers-strategy` must be set or the per-IP limit becomes global (same issue already affects the login limiter).
- Anti-flooding for trial accounts only (user's choice, real accounts are never limited): 20 tickets and 20 comments per hour per account, `429 TRIAL_RATE_LIMIT` with `Retry-After` beyond that; the per-IP account limit stays at 3. Counters are in memory (reset on restart), like the login limiter; `FixedWindowCounter` is now shared by the per-IP and per-account limits.
- Found while testing: the surefire `includes` in `backend/pom.xml` listed only some `unit/` subfolders, so `unit/security` and `unit/controller/business` (AuthController, JwtFilter, LoginAttemptService, the new limiter tests) never ran with `./mvnw test` or in CI. They all passed when run explicitly; the include is now `**/unit/**/*` (357 tests instead of 329).
- Comment rule then replaced by a rank rule for all technicians (user's choice): rank 0 and 1 comment only tickets they created or are assigned to (assigned added after asking: otherwise a rank 1 technician couldn't comment a ticket a manager gave them), rank 2+ and managers/directors/admins comment any ticket. Trial accounts thus comment their own tickets and still can't reach seed tickets. The backend sends a `canComment` flag on ticket detail, like `canSelfAssign`, so the frontend doesn't duplicate the rule. Note: 4 of the 7 seed technicians are rank 1, as is a new technician by default.
- Technician dashboard review: 4 of the 6 "Mes statistiques" cards were hardcoded (prise en charge, appels, résolus/jour, clos/semaine). User's choice: compute "Prise en charge" (assignment → next IN_PROGRESS; near zero for self-assigned tickets), replace the per-day/week ones with averages over the period, and drop "Appels" since the call duration is never entered in the app (only seed data has it). "Résolution" renamed "Temps de traitement": it is time spent in progress, unlike the manager's open → close "Résolution". Also fixed: "Critiques" opened the full active list (now filtered on priority > 75), unclear labels ("Ouverts" → "Actifs", "Aujourd'hui" → "Clos aujourd'hui"), green color on "En attente".
- Period: user chose a 7/30/90/365-day selector (default 30) scoping the statistics and the evolution chart; the workload row stays "now". Previously the frontend silently asked for 365 days.
- Charts (user's pick): evolution (taken in charge vs closed, daily up to 31 days, weekly beyond, zero-filled) and active tickets by status. Status drawn as one-hue horizontal bars in workflow order instead of the manager's donut (comparing close values); both charts follow the DaisyUI theme for text/gridlines, use a validated colorblind-safe pair for series, and have a "Voir les données" table. Not visually checked: the Chrome extension still doesn't connect.
- Bug found in the manager's status chart query: it joined the ticket history, so a ticket that went through its current status twice was counted twice; now joins `Status` on the code directly.

## 2026-11-04

- Technician self-assign route added (assign + start progress in one action, only on tickets the technician created). Goal: let a technician handle a ticket start to finish. A technician who takes a call and can solve it right away shouldn't have to wait for a manager to assign it, possibly to someone else. Restricting it to the creator is deliberate: self-assign is not meant to bypass manager assignment or let technicians pick which tickets they work on (risk of some cherry-picking easy tickets and leaving hard ones to possibly less skilled colleagues). Manager assignment stays the norm for everything else.
- Frontend exposes it in two places: the ticket detail page (shown when the backend's `canSelfAssign` flag is set) and the ticket-created screen of the `ticket-new` wizard, which is the call-taking moment the feature targets.

## 2026-09-08

- Fixed `JwtFilter`: it ran on every route (including public ones like `/log-in`) but didn't catch JWT parsing/validation exceptions, so an invalid/expired/mis-signed `Authorization` header (e.g. after rotating the JWT secret) made the whole request fail instead of just staying unauthenticated. Now catches `JwtException`/`IllegalArgumentException`/`UsernameNotFoundException`, clears the security context, and lets the chain continue; also guards the `Bearer ` prefix before `substring(7)` to avoid a `StringIndexOutOfBoundsException` on a malformed header. Added `JwtFilterUnitTest`.
- Added anti-brute-force protection on `/log-in`: `LoginAttemptService`, an in-memory fixed-window counter keyed by `IP:email` (`app.login.max-attempts`, default 5; `app.login.window-seconds`, default 600). Blocked requests get `429` + `Retry-After`; a successful login resets the counter for that key. Decision: hand-rolled `ConcurrentHashMap` counter instead of Bucket4j — app isn't deployed behind a load balancer or multiple instances, so in-memory state resetting on redeploy isn't a concern, and avoiding the extra dependency was preferred. Window is fixed (resets entirely once expired), not sliding — deemed sufficient for basic brute-force protection. Added `LoginAttemptServiceUnitTest`.

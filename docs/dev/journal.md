# Development journal

History of design/architecture decisions, session milestones, and choices made along the way — **not** a code changelog (see git history for that). Organized by date, most recent session on top. Update at the end of each work session with Claude.

## 2026-10-28

- Admin dashboard KPIs redesigned as data/site-health indicators, in two rows of 6 cards: Tickets (closed without end date — existing; open with a close date; `currentStatus` out of sync with the active `History` row; incoherent assignments; SLA past deadline but not flagged `overdue`; orphan tickets without client/version) and Users (no valid role subtype; password still a `{seed-…}` placeholder; inactive 90 days and never active — both derived from `Activity`, since `AppUser` has no last-login field; accounts with multiple role subtypes, which `AuthController.logIn` silently resolves to whichever role it checks first; admin account count, as a security signal when there is only one or too many). License KPIs and "overloaded technicians" were rejected — the latter is a manager/director concern, not an admin one.
- `DashboardAdminDto` will group KPIs into two nested records (`TicketHealthStats`, `UserHealthStats`) rather than a flat list of fields. The hardcoded "Temps moyen" placeholder section is dropped from the admin dashboard. `UserHealthStats` is only added with the first user KPI, to avoid shipping fields that are always zero: until then, not-yet-implemented cards are rendered with a `null` value (`-`).
- API response time / 5xx metrics deferred to the later charts work: Actuator's Micrometer meters are in-memory and reset on restart, so plotting them over time needs periodic snapshots persisted in the DB.
- Open decision (deferred): how to test the anomaly-detection queries. They detect states the seed data never contains, so meaningful tests need deliberately inconsistent fixtures in DB-backed integration tests (the suite has only `SuiviMnsApplicationTests` today) — more setup than service-level unit tests with mocked DAOs. To be decided later.
- All 12 admin KPIs implemented, one commit each. Ticket rules that a list can filter on are `TicketSpecification` methods shared by the KPI count and a new `TicketSearchCriteria` flag. Specs are written null-safe on purpose: a negated SQL predicate over a NULL column is "unknown" and silently drops rows from the `false` filter (caught on `slaDeadline`). `TicketSpecification.isNotClosed` used to ignore its value (`false` filtered like `true`); `false` now means "has a close date".
- Findings while verifying: overdue/`slaDeadline` are only refreshed on ticket actions (no scheduler → scheduled refresh added to todo, user accepted the SLA KPI being noisy meanwhile); the local Postgres container runs in UTC while the JVM writes zone-less `LocalDateTime` in local time (lead added to Known issues for the ~2h SLA offset); `DemoPasswordSeeder` runs after the "Started" log line, so the first seconds after startup still show placeholder passwords; a user in several role tables silently gets the first role `AppUserDetailsService` finds (client > technician > manager > director > admin) — an admin also listed as client is served the client dashboard; the `"ADMIN"` branch in `AuthController.logIn` is unreachable for role-less users (they get 401 earlier), now documented by a comment.
- Inactive / never-active KPIs count employees only (user's choice over adding a `lastLogin` column or logging logins as activities): logins aren't activities and clients almost never generate any. Admin count KPI is highlighted when there is exactly one admin or more than 5 (user-chosen threshold).
- Verification approach: KPI queries were checked by running the backend (dev profile, port 8099 since the user's IDE instance holds 8080) against the local dev database, injecting anomalies by SQL, then reseeding. User confirmed the local dev DB can be recreated freely for this.
- Decision (user-confirmed): `kpi-card` stays presentation-only and just renders the `colorClass` it is given; each page that uses it decides how to interpret its values into colors. On the admin dashboard, anomaly KPIs turn `text-success` at 0 and keep their alert color otherwise (`healthColor()`), and the admin count has its own rule (`adminCountColor()`).
- `kpi-card` decoupled from navigation, following the same "the page decides" rule as colors: it no longer injects `TicketStoreService`/`Router` nor takes `filters`; it emits `cardClick` and is styled clickable only when the parent listens (`EventEmitter.observed`). Dashboards call `TicketStoreService.openList(filters)` (sets filters + navigates to `/ticket`). The admin "Utilisateurs" cards stay non-clickable: the client list only shows clients while those KPIs are mostly about employees, so an admin users page was put in the todo instead.

## 2026-10-26

- Fixed sidebar active-tab text color: `text-accent-content` is only guaranteed contrasted against `bg-accent`, not against the sidebar's actual `bg-base-200`, so on some DaisyUI themes the active tab label became illegible. Replaced with `bg-base-300 text-base-content font-semibold` (theme-safe pair) on both `nav-desktop` and `nav-mobile`; removed the now-dead `.text-outline` text-shadow workaround from `styles.css`.
- Root-caused the frontend's inconsistent margins/title sizes/layout across pages: `app.html`'s shell gives zero padding around `<router-outlet>`, so every page had been inventing its own spacing/title convention independently (`text-5xl font-bold` on root pages vs `text-3xl` un-bold on detail/form/list pages, forms fixed to `w-xs` ~320px regardless of content, action buttons placed inconsistently).
- Built a shared `app-page-header` component (`components/layout/page-header`) as the fix: owns page padding, title size/weight, and a `pageActions` projected slot next to the title. Migrated onto it: the 4 root pages (dashboard/knowledge/settings/admin), `detail-page` (8 admin detail pages), `generic-form-page` (10 forms — also fixed the `w-xs` bug), `list/title` (8 admin lists — required nesting `app-generic-list` inside `app-title` since they'd been siblings, otherwise the list would've stayed outside the padded area), and the `ticket-new` wizard (deduplicated an identical hardcoded `<h1>` that both wizard steps repeated).
- Decision: `page-header`'s root uses `h-screen flex-col` (viewport units), not `h-full`/percentage height — needed so it can host a full-height column with a pinned footer (ticket-list/client-list). Percentage heights were rejected because Angular component host tags default to `display:inline`, making a percentage-height chain through custom elements unreliable; `h-screen` sidesteps that since it's viewport-relative at every level.
- Per explicit user request, merged `title-bar` + `title-client` into one generic `title-bar` (title/searchPlaceholder inputs, debounced `search` output, `pageActions`/`filters` projected slots), deleting `title-client`. The business logic that had been living inside the header components (role-based ticket filters, closed-tickets toggle + preference persistence, client filters) moved down into the owning pages (`TicketList`/`ClientList`) instead, since a shared header component can't stay wired to one specific store/service. Side effect: `TicketList` now applies the "hide closed tickets" preference *before* the initial `loadTickets()` call instead of the previous two-component ordering that could race.
- Added `app-centered-page` (full-viewport, centered title/subtitle + projected content) for the three no-sidebar routes (`login`, `forbidden`, `not-found`), replacing each page's own ad-hoc centering CSS and inconsistent/missing title styling. Removed the then-dead global `.container` rule from `styles.css` (login was its only consumer, and the rule only half-worked — `justify-content`/`align-items` with no `display:flex`).
- Mid-session, a reported login failure ("mauvais identifiants" on previously-working credentials) turned out to be unrelated to the layout work: `LoginAttemptService`'s anti-brute-force limiter (added just before this session, `1753e25`) was returning 429 after repeated attempts, and the frontend showed the same generic "bad credentials" alert for both 401 and 429. Fixed by distinguishing them in `login.ts` (429 now shows the `Retry-After` wait) and exposing `Retry-After` via CORS in `SecurityConfig` — it's not in the CORS-safelisted response headers, so the frontend couldn't read it cross-origin without that.

Migrated it onto `page-header` (ticket title as page title, "Retour" in `pageActions`, status/priority/id moved to a meta row under the title). `ticket-new` itself was confirmed correct in the build output (page-header present, Tailwind utilities generated) — the visible delta there is just small. ## 2026-09-08

- Fixed `JwtFilter`: it ran on every route (including public ones like `/log-in`) but didn't catch JWT parsing/validation exceptions, so an invalid/expired/mis-signed `Authorization` header (e.g. after rotating the JWT secret) made the whole request fail instead of just staying unauthenticated. Now catches `JwtException`/`IllegalArgumentException`/`UsernameNotFoundException`, clears the security context, and lets the chain continue; also guards the `Bearer ` prefix before `substring(7)` to avoid a `StringIndexOutOfBoundsException` on a malformed header. Added `JwtFilterUnitTest`.
- Added anti-brute-force protection on `/log-in`: `LoginAttemptService`, an in-memory fixed-window counter keyed by `IP:email` (`app.login.max-attempts`, default 5; `app.login.window-seconds`, default 600). Blocked requests get `429` + `Retry-After`; a successful login resets the counter for that key. Decision: hand-rolled `ConcurrentHashMap` counter instead of Bucket4j — app isn't deployed behind a load balancer or multiple instances, so in-memory state resetting on redeploy isn't a concern, and avoiding the extra dependency was preferred. Window is fixed (resets entirely once expired), not sliding — deemed sufficient for basic brute-force protection. Added `LoginAttemptServiceUnitTest`.
